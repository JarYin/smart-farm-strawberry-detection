## 1. วัตถุประสงค์ตามเอกสารโครงการ

จาก `Smart-Farm-Autonomous-Robot.pdf` หัวข้อ "1. บทสรุปโครงการ" ระบุ logic การทำงานหลักไว้ว่า:

```
[กล้อง 320p] -> [AI YOLOv8 วิเคราะห์] -> [พบสตรอว์เบอร์รี/องุ่น: เดินหน้าต่อ]
                                       -> [พบพืชอื่น/วัชพืช: สั่ง Relay เปิดปั๊มพ่นยา]
```

กล่าวคือระบบต้อง **แยกแยะพืชเป้าหมาย (สตรอว์เบอร์รี) ออกจากวัชพืชได้จริง** แล้วสั่งพ่นยาเฉพาะจุดที่เป็นวัชพืช

ตัวชี้วัดความสำเร็จที่เอกสารตั้งไว้ (หัวข้อ 2):
- AI ต้องประมวลผลได้ 7-10 FPS บนบอร์ด Raspberry Pi 4 ด้วยภาพ 320x320 + โมเดล YOLOv8 Nano (TFLite)
- ฮาร์ดแวร์ต้องนิ่งพอลดภาพเบลอ, มีไฟ LED คุมแสง, มีระบบกันน้ำ

## 2. สิ่งที่โมเดลปัจจุบันทำได้จริง

### 2.1 ขอบเขตของโมเดล

| รายการ | ค่าที่พบ |
|---|---|
| จำนวนคลาส | 2 คลาส: `strawberry-ripe`, `strawberry-unripe` |
| คลาสวัชพืช (`weed`) | **ไม่มี** — ไม่เคยถูกเทรนหรือ label ไว้ในเวอร์ชันปัจจุบัน |
| mAP50 (จาก `models/smartfarm_model/eval_per_class.csv`) | strawberry-ripe ≈ 0.848, strawberry-unripe ≈ 0.824 |
| ที่มาข้อมูลเทรน (`notebooks/train_smartfarm_colab.ipynb`) | ภาพสตรอว์เบอร์รีเท่านั้น ไม่มีภาพวัชพืชปนอยู่ |

### 2.2 ผลทดสอบภาพจริง (นอกชุด eval)

ทดสอบด้วยภาพจากภายนอก 3 ภาพ (เก็บไว้ที่ `test_images/`, ผลลัพธ์ที่ `runs/detect/runs_test/predict/`):

| ภาพ | ลักษณะภาพ | ผลลัพธ์ |
|---|---|---|
| `ripe_strawberry_1.jpg` | สตรอว์เบอร์รีสุกลูกเดียว พื้นหลังสะอาด | ✅ ถูกต้อง — `strawberry-ripe` conf 0.89 |
| `ripe_strawberry_2.jpg` | ชามสตรอว์เบอร์รีสุกจำนวนมาก เบียดกัน ระยะใกล้ | ⚠️ **ทายผิด** — ตรวจพบ 34 กล่อง เกือบทั้งหมดถูกจัดเป็น `strawberry-unripe` (conf สูงถึง 0.89) ทั้งที่ทุกลูกสุกแดงจริง |
| `strawberry_plant_1.jpg` | ต้นสตรอว์เบอร์รีในแปลงจริง ใบเยอะ แสงธรรมชาติ | ⚠️ ตรวจจับลูกจริงได้บางส่วน แต่ทายสีผิด (`unripe` ทั้งที่ลูกออกแดง/ชมพูแล้ว) และมี false positive บนใบ/ดินหลายจุด (conf 0.25–0.4) |

**สรุป**: โมเดลแม่นมากกับภาพวัตถุเดี่ยว พื้นหลังสะอาด (สภาพแบบ product photo) แต่ความแม่นยำลดลงชัดเจนเมื่อเจอภาพที่มีผลไม้เบียดกันหนาแน่น หรือภาพภาคสนามจริงที่มีใบ/แสง/พื้นหลังรก — บ่งชี้ **domain gap** ระหว่างข้อมูลเทรน/eval กับสภาพใช้งานจริงในแปลง

### 2.3 ทดสอบ pipeline แบบ end-to-end ผ่านเว็บแคม

รันโปรแกรมหลักจริง (ไม่ใช่แค่ทดสอบโมเดลเดี่ยวๆ):

```
python -m src.main --source webcam --index 0 --headless --mock-relay --record test_images/webcam_test.mp4 --max-frames 60 --no-log
```

ผลลัพธ์ (60 เฟรม, ผลบันทึกที่ `test_images/webcam_test.mp4`):

| รายการ | ค่าที่วัดได้ |
|---|---|
| FPS เฉลี่ย | **8.49** — อยู่ในเกณฑ์เป้าหมาย 7-10 FPS ที่ PDF กำหนด (ทดสอบบน CPU ทั่วไป ไม่ใช่ Pi 4 จริง) |
| เฟรมที่ระบบตัดสินว่าเป็น "วัชพืช" (non-crop-area) | 39/60 (65.0%) |
| จำนวนครั้งที่สั่งพ่น / เวลาพ่นรวม | 2 ครั้ง / 4.91 วินาที |
| สถานะปั๊มตอนจบโปรแกรม | ปิดเรียบร้อย (การปิดปั๊มฉุกเฉินใน `finally` block ของ `src/main.py` ทำงานถูกต้อง) |

**สิ่งที่พบเพิ่มเติมจากการทดสอบสด**: กล้องเว็บแคมหันไปทางห้อง/คน (ไม่ใช่แปลงสตรอว์เบอร์รี) โมเดลตรวจพบ **ใบหน้าคนเป็น `strawberry-unripe` ผิดพลาด (false positive, conf 0.51–0.67)** ในหลายเฟรม และเนื่องจากฉากไม่มีสตรอว์เบอร์รีจริงเลย ระบบจึงอยู่ในสถานะ "non-crop-area" (พร้อมสั่งพ่น) ถึง 65% ของเฟรมทั้งหมด — เป็นการยืนยันด้วยข้อมูลจริงว่าโหมดผกผัน (ข้อ 3) จะสั่งพ่นทุกอย่างที่ไม่ใช่สตรอว์เบอร์รี ไม่ใช่แค่วัชพืช และตัวโมเดลเองก็มีความเสี่ยง false positive กับวัตถุที่ไม่ใช่พืชด้วย ซึ่งอาจทำให้ระบบพ่นยาผิดเป้าหมายรุนแรงกว่าที่ประเมินไว้ในข้อ 2.2

**ข้อสรุปด้าน pipeline**: ส่วนวิศวกรรมซอฟต์แวร์ (กล้อง → โมเดล → ตรรกะตัดสินใจ → สั่งรีเลย์ → ปิดปั๊มปลอดภัยเมื่อจบ) เชื่อมต่อกันถูกต้องและได้ FPS ตามเป้าของ PDF แล้ว จุดที่ยังไม่พร้อมคือความแม่นยำและขอบเขตของตัวโมเดลตรวจจับเอง (ตามข้อ 2.2 และ 3)

## 3. ช่องว่างสำคัญ: ระบบ "พ่นเมื่อพบวัชพืช" ยังไม่ถูกสร้างขึ้นจริง

โค้ดในโปรเจกต์ (`src/logic.py`, `SprayController`) รับรู้ข้อจำกัดนี้อยู่แล้ว และออกแบบทางแก้ไว้ 2 โหมด:

| | โหมดปกติ (`inverse_mode: false`) | โหมดผกผัน (`inverse_mode: true`) — **ใช้งานอยู่ใน `config.yaml` ตอนนี้** |
|---|---|---|
| ต้องมีคลาสวัชพืชในโมเดล | ต้องมี | ไม่ต้องมี |
| ตัดสินใจจาก | กล่องวัชพืชแต่ละกล่องเทียบกับพืชเป้าหมาย | มี/ไม่มีพืชเป้าหมายในเขตพ่น (ROI) |
| ความละเอียดการพ่น | เฉพาะจุดที่เป็นวัชพืชจริง | พ่นทั้งเขต ROI รวมถึงดินเปล่า/พื้นที่ว่างด้วย |
| สถานะปัจจุบัน | ❌ ใช้ไม่ได้ — ไม่มีคลาส `weed` ให้เช็ค | ✅ รันได้ แต่ไม่ใช่การตรวจจับวัชพืชจริง |

**โหมดผกผัน = "ไม่เจอสตรอว์เบอร์รีในเขต ROI → สั่งพ่น"** ไม่ใช่การรู้จำวัชพืช เอกสาร `README.md` (บรรทัด 246-266, 479-486) ระบุตรงๆ ว่าวิธีนี้จะพ่นโดน:
- ดินเปล่า / พลาสติกคลุมแปลง / เงา
- ต้นสตรอว์เบอร์รีที่ยังไม่ออกผล (โมเดลตรวจจับที่ "ผล" ไม่ใช่ "ต้น")
- พื้นที่ใดก็ตามที่โมเดลไม่มั่นใจว่าเป็นสตรอว์เบอร์รี รวมถึงกรณี false negative จากความไม่เสถียรของโมเดลในภาพรก (ดูข้อ 2.2)

**ข้อสรุป**: สิ่งที่ PDF อธิบายไว้ ("พบพืชอื่น/วัชพืช → พ่นยา") ในทางเทคนิคยัง **ไม่ใช่การตรวจจับวัชพืชจริง** แต่เป็นการพ่นแบบ "ไม่ใช่เป้าหมาย = พ่น" ซึ่งกว้างกว่าที่ PDF อธิบายไว้มาก และมีความเสี่ยงพ่นยาเกินความจำเป็น (สิ้นเปลืองยา/น้ำ/พลังงาน) หรือพ่นผิดต้น

## 4. คำถาม: ถ้าเทรนโมเดลใหม่ตามคำแนะนำแล้ว นำไปใช้งานจริงได้เลยหรือไม่

**ยังไม่ได้ทันที** — การเทรนใหม่ (เพิ่มคลาส `weed` + negative sample) แก้ได้แค่ฝั่ง AI/ซอฟต์แวร์เท่านั้น ยังมีอีกหลายจุดที่ต้องทำก่อนใช้งานจริงแบบไม่มีคนดูแล

### 4.1 สิ่งที่เทรนใหม่แก้ได้ตรงจุด
- ให้โมเดลรู้จักคลาส `weed` จริง → เปลี่ยนจากโหมดผกผัน (พ่นทุกอย่างที่ไม่ใช่สตรอว์เบอร์รี) เป็นโหมดปกติที่พ่นเฉพาะวัชพืชจริงได้ (ดูข้อ 3)
- ลด false positive กับวัตถุที่ไม่ใช่พืช (เช่นกรณีตรวจจับใบหน้าคนเป็น unripe ในข้อ 2.3)
- ลด domain gap ถ้าใช้ภาพภาคสนามจริงเทรนเพิ่ม (ตามข้อ 2.2)

### 4.2 สิ่งที่เทรนใหม่ไม่ได้แก้ให้ — ยังต้องทำเพิ่ม

1. **การเก็บ/label ข้อมูลวัชพืช ไม่ใช่เรื่องเล็ก** — ต้องถ่ายภาพวัชพืชจริงที่ขึ้นปนกับสตรอว์เบอร์รีในสภาพแปลงจริง (แสง มุมกล้อง ระยะเดียวกับที่หุ่นยนต์จะเห็น) แล้ว label เอง หรือหา dataset ที่ตรงสายพันธุ์/สภาพแวดล้อมจริง ถ้าใช้ dataset ทั่วไปที่ไม่ตรง ก็จะเจอ domain gap แบบเดียวกับข้อ 2.2 อีก

2. **ยังไม่เคยทดสอบไฟล์ TFLite ที่จะใช้จริงบน Pi เลย** — มี `models/best_float32.tflite` และ `models/best_int8.tflite` อยู่แล้ว แต่ผลทดสอบทั้งหมดในเอกสารนี้ (ข้อ 2.2, 2.3) รันด้วย `best.pt` ผ่าน ultralytics บน PC เท่านั้น ยังไม่เคยวัดความแม่นยำ/FPS ของไฟล์ TFLite บนบอร์ด Raspberry Pi 4 จริง โดยเฉพาะ int8 (quantized) ที่มีโอกาสแม่นยำลดลงกว่ารุ่นเต็มอีก — ต้องวัดซ้ำหลังเทรนโมเดลใหม่ด้วย

3. **ฝั่งฮาร์ดแวร์ยังอยู่แค่ขั้นตอนประมาณราคา** — จาก PDF หัวข้อ 3-4 เป็นแค่ตารางประเมินค่าใช้จ่ายและเปรียบเทียบอุปกรณ์ ยังไม่มีหลักฐานในโปรเจกต์ว่าประกอบตัวรถจริงแล้ว (ตัวรถวิ่งในร่องแปลงนิ่มนวล, ไฟ LED คุมแสง, กล่องกันน้ำ) — ส่วนนี้กระทบความแม่นยำ AI โดยตรงตามที่ PDF เตือนไว้เอง (Motion Blur ถ้ารถสั่น, แสงไม่สม่ำเสมอถ้าไม่มี LED)

4. **ต้องทดสอบภาคสนามแบบมีคนดูแลก่อน** — โค้ดมีระบบนิรภัยพื้นฐานอยู่แล้ว (`min_on_seconds`, `max_on_seconds`, `cooldown_seconds`, ปิดปั๊มใน `finally` เสมอ — ยืนยันแล้วในข้อ 2.3) แต่ยังไม่เคยทดสอบกับปั๊มจริง/ต้นจริง ควรมีคนคุมปุ่มตัดฉุกเฉิน (ปุ่ม `x` ที่มีอยู่แล้ว หรือสวิตช์ hardware) อยู่ใกล้ๆ ระหว่างทดลองรอบแรกๆ เสมอ

### 4.3 เส้นทางที่แนะนำ (ไม่ใช่ "เทรนรอบเดียวจบ")

```
1. เก็บ/label ข้อมูลวัชพืชจริง
2. เทรนโมเดล 3 คลาส (ripe, unripe, weed) + negative sample
3. eval บน .pt ก่อน (per-class, confusion matrix รวม weed)
4. แปลงเป็น TFLite (float32 + int8) แล้ว eval ซ้ำบนไฟล์ TFLite จริง (ความแม่นยำอาจตกจาก quantization)
5. รันบน Raspberry Pi 4 จริง วัด FPS/ความร้อน/ความเสถียร
6. ประกอบฮาร์ดแวร์ (ตัวรถ, LED, กันน้ำ) ตามคำแนะนำใน PDF หัวข้อ 5
7. ทดลองภาคสนามแบบมีคนดูแล + ปุ่มตัดฉุกเฉิน ก่อนปล่อยทำงานอัตโนมัติเต็มรูปแบบ
```

พูดง่ายๆ คือ **การเทรนใหม่คือก้าวแรกที่จำเป็น ไม่ใช่ก้าวสุดท้าย** — เป็น prototype ระดับ AI/ซอฟต์แวร์ที่ต้องผ่านการตรวจสอบ TFLite + ฮาร์ดแวร์ + ภาคสนามอีกหลายรอบก่อนถึงจะเรียกว่า "ใช้งานจริง" ได้อย่างปลอดภัย

## 5. ข้อเสนอแนะ

1. **ถ้าต้องการให้ตรงสเปก PDF จริง (แยกวัชพืชได้)**
   ต้องเก็บ/หา dataset ภาพวัชพืชที่ label แล้ว เพิ่มเป็นคลาสที่ 3 (`weed`) แล้วเทรนโมเดลใหม่ให้รู้จัก 3 คลาส (`strawberry-ripe`, `strawberry-unripe`, `weed`) — เป็นทางเดียวที่จะทำ logic ตรงตาม PDF ได้จริง

2. **ถ้าเวลา/ทรัพยากรจำกัด (ระดับ Prototype)**
   ใช้โหมดผกผันต่อไปได้ แต่ควรระบุในรายงานให้ตรงกับความเป็นจริงว่าเป็น **"non-crop-area spraying"** ไม่ใช่ "weed detection" และลดความเสี่ยงพ่นผิดโดย:
   - จำกัดพ่นเฉพาะโซน ROI แคบ ไม่ใช่ทั้งเฟรม (ตามที่ README แนะนำไว้)
   - เพิ่มเงื่อนไขยืนยันหลายเฟรมก่อนสั่งพ่น (ไม่ตัดสินจากเฟรมเดียว) เพื่อกัน false trigger จากความไม่เสถียรของโมเดลในภาพรก

3. **ปรับปรุงความแม่นยำของโมเดลจำแนก ripe/unripe**
   จากผลทดสอบข้อ 2.2 โมเดลควรได้ fine-tune เพิ่มด้วยภาพภาคสนามจริง (มีใบ, แสงธรรมชาติ, ผลเบียดกัน) ไม่ใช่แค่ภาพ product photo พื้นหลังสะอาด เพื่อลด domain gap ก่อนนำไปใช้งานจริงกับหุ่นยนต์

4. **ส่วนที่ตรงเป้าหมาย PDF อยู่แล้ว**
   ความสามารถ "สแกนตรวจจับพืชเป้าหมาย" (ripe/unripe) ทำงานได้ดีในสภาพภาพที่เหมาะสม ตรงกับเป้าหมายข้อนี้ของ PDF — เป็นจุดแข็งที่ใช้ต่อยอดได้ และจากการทดสอบ pipeline สด (ข้อ 2.3) ยืนยันว่าโครงสร้างซอฟต์แวร์ กล้อง→AI→ตรรกะ→รีเลย์ เชื่อมกันถูกต้องและได้ FPS ตามเป้าของ PDF แล้ว

5. **เพิ่มความทนทานต่อ false positive กับวัตถุที่ไม่ใช่พืช**
   การทดสอบเว็บแคมสด (ข้อ 2.3) พบว่าโมเดลตรวจจับใบหน้าคนเป็น `strawberry-unripe` ผิดพลาดได้ ก่อนใช้งานจริงควรเพิ่มภาพพื้นหลังทั่วไปที่ไม่มีพืช (คน, วัตถุในบ้าน, ท้องฟ้า ฯลฯ) เป็น negative sample ตอนเทรน เพื่อลดโอกาสระบบสั่งพ่นยาผิดเป้าหมายรุนแรงกว่าที่คาดไว้ในโหมดผกผัน
